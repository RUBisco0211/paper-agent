# 0095 队列按「我的未完成请求」组织，项目关联随请求记录

- DATE: 2026-10-26
- TAGS: data, ingest, product, frontend
- STATUS: 当前
- SUPERSEDES: 0094 中「队列以 downloads 为行」与「下载成功后接入 run」的表述

## DECISION

**队列是「我的未完成请求」，不是「我的每次下载」。** 上传与标识符导入都会留下一条请求记录（`user_runs`），下载成功时该记录指向它接入的 run。队列取 `downloads` 与 `user_runs` 的并集，同一 run 只显示一次：若我的某条 `downloads` 的 `run_id` 已是这条 run，则由那条下载代表，`user_runs` 不再单独出现。

**`user_runs` 一行代表「我在等这条 run」，因此 `(user, run)` 唯一。** 用户请求一篇已处理完成的论文时，不写 `user_runs`，直接建立 `user_papers`（若指定项目，一并写入 `project_papers`）：没有任何东西可等，队列不该为它留位。上传一篇已在库的论文因此不出现在队列里，用户在文献库直接看到它。

**`user_runs.project_id` 表示这次请求要把结果同时放进哪个项目**，可空。请求接受时校验项目属于当前用户，不属于立即报错，不进入队列。run 成功时按 `paper_id` 反查所有 `user_runs`，先建 `user_papers`，再对有 `project_id` 的记录建 `project_papers`。

**`project_papers` 的归属由写入时校验保证。** 只有「当前用户自己可见的条目」才会被加入其项目，因此项目内不会出现该用户看不到的论文。

**列表与详情的分工。** 列表只表达这件事当前的状态（等待 / 处理中 / 已完成 / 失败），不区分有没有下载。详情按实际发生过的动作列步骤：标识符导入显示「获取原文」加解析、切块、生成向量（`runs` 的三个阶段）；上传显示「文件上传」加同样的三个阶段。

## REJECTED

- 队列只读 `downloads`：上传没有下载记录，用户点完看不到任何痕迹。
- 为已完成的论文也写 `user_runs`：同一用户对同一 run 会出现第二行，与 `(user, run)` 唯一冲突，或迫使队列按请求而非按 run 组织。
- 在 `user_runs` 上加 `download_id` 做去重：多一列只为省一次按 `run_id` 的关联查询，而该查询本就在队列这一处。
- 列表上区分「带下载」与「不带下载」两种形态：用户关心的是进度，属于详情的细节。

## RATIONALE

用户心智里只有一件事——「我提交的东西怎么样」。上传与导入只是取得文件的手段不同，在队列里都应当是同一种请求；而项目归属属于「谁要的」，与论文本身无关，因此跟着请求走，不挂在 `papers` 或 `runs` 上。已经可用的论文没有被等待的东西，直接拥有即可。

## OUT OF SCOPE

一次请求加入多个项目；请求记录的历史清理策略。

## OPEN

无。

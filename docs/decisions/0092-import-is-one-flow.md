# 0092 入库是一条导入流程，元数据不占流程

- DATE: 2026-10-24
- TAGS: ingest, data, product
- STATUS: 当前
- SUPERSEDES: 0019、0056 的任务模型；0058 的阶段命名

## DECISION

**一次入库 = 一条 `paper_imports` 记录，一篇论文只有一条。** 直接上传与 DOI/arXiv 导入是同一条流程的两种来源，差异只在第一个阶段取文件的手段。导入记录不属于某个用户的请求：同一文件被第二个人导入时复用同一条记录，只新增收藏关系。记录保留 `initiated_by` 表示谁先发起，仅作追溯，不参与权限与可见性。

**流程有四个阶段：`source / parse / chunk / embed`。** `source` 把原文拿到手（下载或上传即得，故不叫 download）；四者全部成功才是 `ready`。阶段状态存 `import_stages` 子表，一条导入对四行。`ingestion_jobs` 与 `ingestion_stages` 取消，`ingestion` 一词不再出现在代码、表名与文案中；并发按阶段分别控制，因为四个阶段的瓶颈分别是网络、MinerU 每日页数、本机 CPU 与向量服务的 token 限额。

**元数据不占流程。** 它只依赖原文文件，与解析、切块、向量化无同步关系，因此在 `source` 成功后静默查询，失败不打扰任何人，也从不阻断 `ready`。查过与否由 `metadata_sources` 是否为空判断，不设状态枚举。

**未完成不进文献列表。** 原文一落库、论文行一建立，就创建用户的收藏条目并标 `ready = false`：它能出现在导入队列里，但不进文献列表，直到四个阶段全部成功才置 `ready = true`。因此 `paper_id` 从建立时就有值，不需要任何「待完成」指针字段；`papers` 只是具体文件的索引。进度只在导入队列展示，重试入口也只在导入队列，重跑整条流程并跳过已成功阶段。

**arXiv 版本号参与身份。** arXiv 标识符带版本号时存完整形式（`1706.03762v7`），因为它恰好指向一个文件；导入前先按它查本地，命中且文件仍在就直接复用，不重新下载。DOI 与不带版本的 arXiv 不做此复用，因为它们可能对应多个文件。对象存储的键只由文件哈希决定，所以清理数据库时无需清理存储。

## REJECTED

- 保留 `ingestion_jobs` 与 `paper_imports` 两张表：同一条流程被记录两次，状态必须互相同步，同步失败即漂移。
- 把元数据作为第五个阶段：它失败就会阻断整篇论文，而可解析、可检索的论文本可脱离书目使用；且它没有并发竞争的必要。
- 只允许 DOI/arXiv 导入建导入记录：上传路径的处理状态就没有归属。
- 在 `papers` 上保存阶段布尔或完成标志：与产物脱节后会出现「标志说解析过、存储里没有产物」，重试永远修不好。
- 任务表用 `paper_id` 作身份而无导入记录：同一篇论文被多人导入时无法表达「谁触发的、进行到哪」。

## RATIONALE

用户界面只有一条进度，后端也应当只有一个进度。把「谁发起」「入到哪篇论文」「产物是否就绪」分别交给导入记录、收藏关系与产物自身，三处各答一问，不再互为副本。

## OUT OF SCOPE

拆分阶段任务的并发调度实现；开放源 PDF 覆盖率改进；用户自定义书目覆盖层。

## OPEN

旧数据清理方式见迁移与 `scripts/clear_paper_data.py`；真实 MinerU 与向量链路需在小体量样本上回测。

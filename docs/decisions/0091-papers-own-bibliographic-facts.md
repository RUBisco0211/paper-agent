# 0091 文献与条目分离：书目只有一份，阶段名说它测什么

- DATE: 2026-10-24
- TAGS: library, ingest, data, product
- STATUS: 当前
- SUPERSEDES: 0019 的「能力与状态分离」表述、0056 的「用户条目可先于全文存在」相关片段、0058 的阶段命名

## DECISION

**文献与收藏条目分开，书目只有一份。** `papers` 是文献本体，独占书名、作者、摘要、年份、期刊、DOI、arXiv 号与元数据来源；`user_papers` 只记录谁收藏了哪篇以及如何进入（`source`），不再保存任何书目副本。用户不能编辑书目，唯一写者是系统自动查询。

**文献必然带原文。** `papers.file_hash` 保持非空唯一；`user_papers.paper_id` 非空。上传 PDF 与 DOI/arXiv 导入都以「取得原文」为前提：导入取不到公开全文就是这次导入失败，界面提示找不到源文件，不留下只有元数据的条目。

**阶段名描述产物，不描述笼统的「全文」。** 能力标志改为 `has_source`（原文已入库）、`has_metadata`（书目就绪）、`has_parsed`（解析出可读正文）、`has_index`（已切块可检索）、`has_embedding`（已向量化）。处理阶段为 `metadata → parse → chunking → embedding`，`fulltext` 一词不再出现在代码与文案中。

**只保留一个重试入口。** 现有任务的失败通过任务重试从失败处跑到底；不再提供「重新获取全文」「获取元数据」「编辑信息」「给已有条目补传 PDF」这些单步入口。

## REJECTED

- 条目保存书目副本并允许用户修改：两份记录会各自漂移，界面与流水线对「元数据是否就绪」判断不一致。
- 允许 `papers` 没有原文、靠 NULL 文件哈希存放未下载文献：身份从「一篇文献」退化为「一个待办」，同标识符会重复建行，还要再写一套合并逻辑。
- 导入取不到全文时保留「待补全文」条目：条目无法自行变得可用，用户也没有合法手段补齐，只会长期占据列表。
- 把下载并进处理流水线作为第一个阶段：任务必须挂在已有文献上，而无原文时文献不存在，强行加入就要允许 `papers` 没有文件。
- 保留 `fulltext` 作为阶段名：它同时指「文件已入库」和「已解析出正文」，文案无法自洽。

## RATIONALE

用户界面上始终只有一条进度；后端却把它拆成导入记录与处理任务两套状态，还让同一份书目存在两张表里，界面只能靠合并两套标签表伪装成连续进度。把书目收归一处、把条目降为关系、让阶段名对应可验证的产物，进度就不需要再被拼装。

## OUT OF SCOPE

拆为阶段级任务与各阶段独立并发（另立决策）；开放源 PDF 覆盖率的改进；用户自定义书目（后续如需要，应作为独立的覆盖层而不是条目副本）。

## OPEN

存量数据的清理方式见迁移 `20261024_0036` 与 `scripts/clear_paper_data.py`；真实 MinerU/向量化链路需在清理后重新跑一遍小体量回测。

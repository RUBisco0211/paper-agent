# 0033 前端以 web_ui 样式为底座，在此基础上扩展

- DATE: 2026-10-05
- TAGS: frontend
- STATUS: 当前
- SUPERSEDES: `docs/frontend/ui-spec.md` §2–§6（已删除，降级为扩展时的参考）

## DECISION

以 web_ui 的样式与组件体系为**底座**，不推翻、不重做；在此之上**扩展**本项目特有部分。判定规则：**上游已有等价能力直接沿用，没有的在它的体系内扩展，而不是另起一套。**

- 直接沿用：布局骨架、会话消息渲染、SSE 流式呈现、工具调用与结果渲染、中断 UI、基础 shadcn 组件集。
- 自行扩展：论文库、项目与会话范围、引用原文卡片、会话列表按项目分组（未分组在最前，每组可折叠，组内按创建时间倒序；删除/改名放行内菜单或悬浮操作）。扩展组件一律 shadcn + `radix-nova`（0014），复用上游 token、图标与动效，不引入第二套方言或设计 token；原 ui-spec §2–§6 的组件映射表、图标规范、夜间模式与动效细则不再强制，降级为扩展时的参考。

## REJECTED

- 把 ui-spec 的 ChatGPT 式侧边栏整体覆盖到 web_ui 上：推翻上游骨架，同步时持续冲突。另起一套设计 token、第二套 shadcn 方言（`base=radix`）或自建组件库同理，会让扩展组件与上游视觉不一致。
- 手写气泡与滚动容器替代上游消息渲染：重复实现上游已做好且最易出错的部分。

## RATIONALE

两边同为 shadcn 生态，扩展成本在业务逻辑而非视觉；而上游已做好的消息渲染（流式、工具结果、中断）恰是重构中成本最高、最容易出错的部分，直接继承最划算。会话按项目分组是产品结构，属于扩展而非视觉规范。

## OUT OF SCOPE

重做上游布局骨架、自建设计系统、i18n。

## OPEN

上游消息渲染如何承载「引用原文卡片」这类自定义内容块（自定义 block 渲染器 vs 塞进 markdown）。

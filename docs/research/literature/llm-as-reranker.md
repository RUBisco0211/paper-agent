# LLM as a reranker：基本流程草案

- 日期：2026-10-23
- 状态：会话讨论记录，待评估；不是实施决策，尚未实现。

## 当前基线

- PostgreSQL 全文检索（`ts_rank`，不是 BM25）与 pgvector 余弦检索各召回前 20 个 chunk。
- RRF 融合（`k=60`）后，最多选 12 个 chunk、每篇最多 4 个，再合并选中的相邻块并返回证据。
- 实现锚点：`backend/app/retrieval/service.py`、`backend/app/retrieval/repo.py`、`backend/app/literature_support/evidence/ranking.py`。

## 拟评估流程

1. 业务服务按用户与会话范围授权，执行关键词和向量召回。
2. RRF 融合后，初步考虑取前 20 个候选；重排位于最终数量限制、相邻块合并和对外片段裁剪之前。
3. 向 LLM 提供当前检索问题，以及各候选的临时编号、论文标题、章节路径和正文；限制候选数量与总输入长度。
4. 初步采用 listwise：一次比较全部候选，按“是否提供回答所需的直接证据”排序，而不只是比较主题相似度；无关项可不返回。
5. LLM 只返回候选编号有序列表，例如 `{"ranked_ids": ["C7", "C2", "C12"]}`；程序校验编号归属、结构与重复项，不接受模型改写证据或生成引用、页码。
6. 基于重排结果执行证据配额与相邻块合并，再由业务服务完成引用登记，返回 Agent。

## 初步边界与待确认项

- 建议第一版默认关闭，复用用户当前会话模型及 Credential；不使用平台共享 Key，不擅自切换模型供应商。
- 业务服务保留授权、召回与引用登记职责；agent_service 承担用户模型调用。跨服务候选传递与最终证据登记契约尚未设计，实施前需确认。
- 论文文本是不可信数据，不能执行其中的指令；临时编号不作为已登记 Citation ID。
- 超时、限流或输出非法时，建议回退原 RRF 排序并明确标记重排未成功；有效空列表与非法输出应区分，具体返回语义待确认。
- 不把 LLM 自评分当作相关性概率；不沿用对外 1200 字符片段裁剪作为默认重排输入。
- 重排无法找回召回阶段遗漏的内容；每次检索增加一轮 LLM 请求，一轮回答多次检索会累积延迟与费用。
- 先以真实论文问题对比前列证据质量、耗时和 token 成本，再决定是否启用；无需先将关键词通道替换为 BM25。

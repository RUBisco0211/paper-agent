## 已由仓库确定的事实（不再反问）

- 当前仓库是 FastAPI 模块化单体骨架，`todo` 领域为垂直切片示例；论文相关功能尚未实现。
- ORM 基线 SQLAlchemy 2.0 + Alembic；日志 structlog + `X-Request-ID`；Python 固定 3.13。
- 原型里 Docker Compose、GROBID、MinIO、Celery、pgvector、AgentScope 等仍是选型，尚未成为代码依赖。

## 项目定位（用户提供，影响所有模块的取舍）

- 本仓库是**简历项目**：目标是展示完整架构与工程能力，交付质量要配得上简历。
- 省掉的是"不展示工程能力的非核心产品细节"（例如数据出站的合规披露 UI）；**不代表降低架构/工程质量**——工程、状态机、RAG 链路、测试要做扎实。
- 形态为多用户后端项目，用户经网页前端访问；「面向个人」= 每个使用者是独立个人用户。
- 前端由独立方向/后续实现，本仓库交付纯后端 API；验收用 Yaak 做 API 测试。
- 首版输入范围限定为英文 born-digital 学术 PDF；暂不支持中文论文，不承担中文分词与中文关键词检索能力。

# 模块 01：产品边界与 MVP

> 目标：先锁定"首版为何存在、服务谁、承诺什么"。这是数据模型、状态机和 API 的共同前置。Round 1 问的是最根本的产品分叉。

## Round 1（当前激活）

❓ **Q1 - 首版部署形态与账户模型（根本分叉）**：原型同时写着"面向个人、私有化部署"，又设计了多账户 `users` 表 + 跨用户全局论文去重。这个矛盾不解决，认证、隔离、成本承担全会跟着摇摆。首版到底承诺哪种形态？

- A：单实例单所有者，一个账号、不开放注册（内部保留 `user_id` 边界以便未来扩展）
- B：单实例多账号，互相隔离但允许注册
- C：一开始就按多租户安全做

➡️ 推荐答案：A。首版单用户私有部署，架构上预留 `user_id`，但不承担完整多租户的安全与配额成本。

✅ 决定：**多用户后端项目，用户通过网页前端访问；「面向个人」指每个使用者是独立个人用户，不是单所有者。**
- 对原型的修正 1：原型"不实现前端界面（仅提供 API）"需修订为"后端服务 + 网页前端访问"。
- 对原型的修正 2：多账号（注册/登录/权限过滤）是必要能力，不再是可选项。
- 影响：跨用户全局论文去重需在多账号下重新定义隔离与权限；认证成为模块 02 的硬前置；安全基线（模块 10）随之上升。

❓ **Q2 - 最小核心闭环**：首版必须让用户完整走通的最小闭环是什么？"上传 → 看见处理状态 → 在论文/项目范围内问答 → 结论带出处"是否就是完整闭环？论文库管理、项目、独立搜索页是必要能力还是辅助？

➡️ 推荐答案：核心闭环为"上传 → 可理解的解析状态 → 项目范围内问答 → 关键结论可回到原文"。论文库和项目只做支撑闭环所需的最小管理，不做独立搜索页。

✅ 决定：**接受推荐。** 核心闭环 = 上传 → 可理解的解析状态 → 项目范围内问答 → 关键结论可回到原文。论文库与项目只做支撑闭环的最小管理，不做独立搜索页。

❓ **Q3 - 问答质量的产品承诺**：问答"可用"的验收标准是什么——只要给出自然语言答案，还是必须关键事实可定位到原文、显式区分"论文陈述 / 跨文综合 / 模型推断"、证据不足时说明缺口而非用通用知识填充？

➡️ 推荐答案：关键事实必须可溯源到原文位置；回答显式区分论文事实与模型推断；证据不足时明说，不用通用知识伪装成论文内容。

✅ 决定：**接受推荐。** 关键事实必须可溯源到原文位置；回答显式区分论文陈述/跨文综合/模型推断；证据不足时说明缺口，不用通用知识填充。

❓ **Q4 - 数据出站边界**：私有化部署不等于全本地——PDF 发给 MinerU、文本发给 Embedding、问题与检索片段发给 LLM 都是必要出站。用户需要多细的可见性和控制？是否要在配置/API 里明确"哪些数据发给了哪家供应商"、允许最小化发送？

➡️ 推荐答案：允许必要出站，但配置与文档明确列出各类数据流向；默认最小化发送内容；禁止静默把整库或无关上下文发给 LLM。

✅ 决定：**本仓库是简历项目，不做额外的数据出站披露/控制层。** 数据流向仅在 README/文档中说明，不提供配置开关或用户级控制界面。

❓ **Q5 - 首版明确不做什么**：原型"后期可能增加"清单（联网搜论文、相似论文、笔记/标注、专用 Agent、定时 workflow、引文网络）中，是否有任何一项必须进入首版验收？还是全部排到首版之后，只为其预留扩展接口？

➡️ 推荐答案：全部不进首版验收；现在只为 Tool / Run 扩展留清晰边界，不预先实现工作流引擎、引文图谱或通用文档系统。

✅ 决定：**接受推荐。** 联网搜论文、相似论文、笔记/标注、专用 Agent、定时 workflow、引文网络全部排到首版之后，不预先实现；只为 Tool / Run 扩展留清晰边界。

❓ **Q6 - 纯后端如何被验证和使用**：没有前端时，首版靠什么被验证？只交付 OpenAPI 可调用就够，还是必须提供可复制的 HTTP 示例、端到端验收脚本、乃至 CLI 或管理接口？

➡️ 推荐答案：交付 REST/SSE API + 完整 OpenAPI + 可复制的 curl/HTTP 示例 + 端到端验收脚本；不做正式 CLI 或前端，但不允许把只能靠改数据库完成的操作留给使用者。

✅ 决定：**当前没有对应前端；后端交付为纯 REST/SSE API，验收/联调用 Yaak（API 测试工具）创建 API 测试。**
- 前端由独立方向/后续迭代实现，不在本仓库范围。
- 影响：OpenAPI 需能被 Yaak 稳定消费；验收脚本可落到 Yaak 请求集合；原型"不实现前端界面"与 Q1"网页前端访问"的衔接由此闭合。

## Round 1 结语（分支归属）

- 认证最小形态：Q1 已定为多用户 → 认证是必要能力，具体设计移到模块 02。
- 解析部分成功能否提前使用：移到模块 04（状态机 / 能力判定）。
- 端到端验收场景与质量阈值：以"核心闭环 + Yaak API 测试集合"为验收载体，细化到模块 09（API）定义。
- 哪些未来能力成为当前架构约束：Q5 已定——只留 Tool / Run 扩展边界，不实现工作流引擎、引文图谱、通用文档系统。

# 模块 02：账户、认证与供应商配置

> 前置：模块 01 已定"多用户后端 + 网页前端访问"。目标：认证做到什么程度、Key 属于谁、多账号下论文可见性如何。

## Round 1（当前激活）

❓ **Q1 - 认证最小面**：多账号确认后，首版认证流程做到哪一步？注册、登录、访问令牌、刷新令牌、登出是否够？邮箱验证、找回密码、角色/管理员是否进首版？

- A：注册 + 登录 + JWT 访问令牌 + 刷新令牌 + 登出（够像样的简历项目）
- B：仅预置一个账号 + 登录后签发 Bearer，无注册
- C：A + 邮箱验证 + 找回密码 + 角色/管理员

➡️ 推荐答案：A。邮箱验证、找回密码、管理员角色后置，首版不做。

✅ 决定：**接受推荐 A。** 注册 + 登录 + JWT 访问令牌 + 刷新令牌 + 登出；邮箱验证、找回密码、管理员角色后置。

- 访问令牌使用短期 JWT，有效期默认 15 分钟；服务端不逐请求查 token 表。
- 刷新令牌使用高熵随机值，有效期默认 7 天；数据库只保存其哈希、所属用户/登录会话、过期时间和撤销状态，不保存明文。
- 每次刷新在数据库事务中轮换：旧 refresh token 立即失效，签发新的 access token 与 refresh token；并发重复刷新只能有一个成功。
- 检测到已轮换 refresh token 被再次使用时，撤销该登录会话的整个 token family，降低令牌泄露风险。
- 登出撤销当前登录会话的 refresh token family；已有 access JWT 最多继续有效至 15 分钟到期。密码修改或“全部登出”可撤销该用户全部 refresh sessions。
- 浏览器端 access token 仅保存在运行时内存；页面硬刷新后调用 `/v1/auth/refresh` 获取新 access token。Refresh token 只通过 `HttpOnly + Secure` Cookie 保存和发送，前端 JavaScript 不读取；普通业务 API 继续使用 Bearer access token。

❓ **Q2 - 密钥存放与归属**：MinerU / Embedding / LLM Key 放哪、属于谁？原型把 Key 放 `preferences` JSONB，会与普通偏好混在一起。

- A：环境变量提供实例默认；用户可在设置填自己的 Key，单独 credential 记录、应用层加密、API 永不回显明文
- B：全部实例级环境变量，用户不配置（"用户自备 Key"名存实亡）
- C：全部用户级配置，无实例默认

➡️ 推荐答案：A。呼应"用户自备 Key"的产品承诺，同时不把秘密塞进 JSONB 偏好。

✅ 最新决定（2026-09-19）：**目录选择 + 用户 API Key。**
- MinerU 与 Embedding 仍为实例级配置。
- LLM Provider 与模型只能从 AgentScope Model Card 目录选择，用户只输入 API Key；不允许自由输入 Provider、模型或 Base URL。
- LLM Key 保存在浏览器，随 Agent 启动/恢复请求传入，不进入数据库、日志、Entry、对象存储或任务队列。

❓ **Q3 - 供应商配置作用域**：同一配置项（如 LLM 模型、Embedding Key）在实例、用户、run 三级怎么覆盖？

- A：实例默认值 < 用户默认值 < 单次 run 显式选择；首版不做项目级覆盖
- B：仅用户级配置，无实例默认
- C：增加项目级覆盖

➡️ 推荐答案：A。三级覆盖清晰且可测，项目级留到未来。

✅ 最新决定（2026-09-19）：**Embedding 实例级，LLM 用户从目录选择。**
- 用户不能定义模型名称，只能选择后端发布的 Provider/模型组合并填写自己的 API Key。

❓ **Q4 - 跨用户论文可见性**：原型是全局唯一 `papers`（按 file_hash 去重）。多账号下，A 上传的论文 B 能看到吗？解析/向量产物怎么复用？

- A：`papers` 全局唯一，但只有经 `user_papers` 关联的用户可见、可检索；解析与向量产物按 embedding 配置版本复用，不暴露"别人是否上传过该论文"
- B：每用户独立副本，严格隔离
- C：全库公开共享

➡️ 推荐答案：A。保持去重收益，同时用关联表做权限边界。

✅ 决定：**接受推荐 A。** papers 全局唯一（按 file_hash 去重），只有经 user_papers 关联的用户可见、可检索；解析/向量产物按 embedding 配置版本复用，不暴露"他人是否上传过该论文"。

❓ **Q5 - 成本与额度**：谁承担远程 API 成本？鉴权失败、额度不足、限流、供应商故障如何让用户/开发者区分？

- A：成本归 Key 所属用户；任务状态用稳定错误码区分鉴权 / 额度 / 限流 / 供应商故障
- B：不做用量统计，错误文案可读即可
- C：完整用量统计面板（超出简历项目范围）

➡️ 推荐答案：A。只记录 run 的 usage 字段与稳定错误码，不做统计面板。

✅ 决定：**接受推荐 A。** 成本按 Key 归属自动归因（LLM 归用户前端 Key、MinerU/Embedding 归实例 env Key）；失败用稳定错误码区分鉴权/额度/限流/供应商故障；run 记录 usage（token 数）；不做统计面板。

# 模块 03：论文库、项目与生命周期

> 前置：模块 02 已定 papers 全局唯一 + user_papers 关联隔离。目标：项目怎么建模、库/项目/删除的分层语义、元数据归属、项目上下文如何影响会话。

## Round 1（当前激活）

❓ **Q1 - 项目如何建模**：原型 `projects.paper_ids` 用 JSONB 存 ID 数组。多项目复用同一论文、排序、删除、跨项目统计时 JSONB 还够用吗？要不要规范化为关联表？

- A：规范化 `project_papers` 关联表（含 added_at、排序），不用 JSONB
- B：保持 JSONB 数组（最简，但排序/删除/跨项目查询别扭）
- C：首版只做"论文库"，项目推迟（但"项目范围内问答"是核心闭环，需要范围概念）

➡️ 推荐答案：A。关联表支撑排序与权限过滤更自然。

✅ 决定：**接受推荐 A。** 规范化 `project_papers` 关联表（含 added_at、排序），不用 JSONB 存 paper_ids。影响：原型 `projects.paper_ids` 字段废弃。

❓ **Q2 - 重复添加语义**：同一用户再次上传/添加相同文件时，返回已有论文、报冲突，还是创建新条目？

- A：幂等返回已有论文关联，并可选地本次加入指定项目
- B：报 409 冲突
- C：创建新条目（违背模块 02 的全局去重）

➡️ 推荐答案：A。幂等体验最好，也符合全局去重。

✅ 决定：**接受推荐 A。** 同一用户重复添加/上传相同文件 → 幂等返回已有论文关联，并可选地本次加入指定项目。

❓ **Q3 - 论文身份与版本**：预印本、期刊版、修订版、字节不同但内容相近的 PDF 如何关联？

- A：首版只承诺文件级 SHA-256 去重；DOI/标题相似仅作元数据提示，不自动合并
- B：内容级模糊去重合并（复杂，超出范围）

➡️ 推荐答案：A。文件级去重足够支撑 MVP，自动合并风险高。

✅ 决定：**接受推荐 A。** 文件级 SHA-256 去重；DOI/标题相似仅作元数据提示，不自动合并不同文件。

❓ **Q4 - 删除层级**："移出项目"、"移出论文库"、"物理删除对象"分别何时发生？共享对象何时被清理？

- A：前两者同步解除关联；物理删除只在无任何用户引用且过保留期后由后台清理
- B：删除即物理删除（简单但有风险）
- C：只软删除，物理删除永远手动

➡️ 推荐答案：A。区分"解除引用"与"清理实体"两级，避免删了别人的论文。

✅ 决定：**用户自定义（机制导向）：以 `user_papers` 多对多关联表承载关系。**
- **后续范围修正：首版不提供从个人论文库主动移除论文的 API。** `user_papers` 在当前版本只新增，不处理用户主动删除、恢复、历史引用失效或无主论文清理；这些行为后期统一讨论。
- 首版仍需清理未完成上传、校验失败及解析流程产生且未绑定有效 paper 的临时对象，但这不属于用户删除功能。

❓ **Q5 - 元数据归属**：标题/作者等解析元数据是全局论文事实；用户修正、标签、阅读状态放哪？（papers 全局唯一、多人复用）

- A：解析元数据保留原始值 + 来源；用户修正/标签/状态放用户关联层
- B：全部放 papers.metadata JSONB，用户直接改全局
- C：首版不提供用户编辑元数据的能力

➡️ 推荐答案：A。改全局会污染别人看到的论文。

✅ 决定：**接受推荐 A。** 解析元数据保留原始值 + 来源（全局论文事实）；用户修正/标签/阅读状态放用户关联层（user_papers 扩展字段或独立表），不污染全局。

### 补充确认：user_papers 的领域职责

- 保留 `user_papers`，并将其视为“用户论文关系实体”，而不只是无业务含义的连接表。
- 当前版本只承载用户将全局 paper 纳入个人论文库所需的关系与生命周期字段，不实现阅读行为功能。
- 未来可在该关系上增加阅读状态、收藏、最近阅读时间等当前状态；需要追加式行为历史时另建 activity/event 表，不把事件数组塞入 `user_papers` JSONB。
- 原先关于 `user_papers` 硬删除及全局 paper 7 天 orphan 保留期的选择，因首版取消主动删除功能而不再进入实现；保留为未来删除功能设计参考。

❓ **Q6 - 项目上下文与会话**：会话绑定项目后，项目论文集合变化是否影响旧会话/旧 run？

- A：新 run 读取项目当前集合，并保存本次 run 的论文范围快照用于复现
- B：旧会话永远用旧集合
- C：动态跟随、无快照

➡️ 推荐答案：A。快照保证历史 run 可复现，当前集合保证提问用最新范围。

✅ 决定：**项目论文集合不作为静态上下文直接注入会话，由 Agent 工具（list_project_papers / search_papers 等）在生成过程中动态获取。**
- session 归属于 project，但不冻结固定论文范围；提问时使用项目当前论文集合。
- 历史复现依据是 entry 日志中记录的实际工具调用、检索证据与引用，不另建 run 快照。
- 涉及模块：06（检索作用域）、07（agent 工具与权限）。

### 补充确认：session 与 project

- **修正：session 可以不属于 project，`sessions.project_id` 可空。** 创建会话时可选传入当前用户拥有的 `project_id`。
- `project_id IS NULL` 表示个人全库会话，Agent 默认可见当前用户通过 `user_papers` 关联的全部论文。
- `project_id` 非空时表示项目会话，项目论文集合是 Agent 文献查询工具的硬边界，不能检索项目外论文。
- 用户可以通过普通项目 API 手动把个人论文库中的论文追加到项目，新增论文随后对项目会话可见；这是渐进式披露，不冻结创建会话时的集合。
- 首版不允许从项目移除论文，避免已经产生的引用失去项目可见性；是否支持移除后期再讨论。
- LLM 只获得只读的文献列举、搜索和取原文工具，不获得修改 `project_papers` 的工具。两种会话的实际工具调用、证据与引用都记录为 entries。
- 首版允许删除项目：服务先终止项目内所有活动 Agent，清空 pending，级联删除 sessions、Redis 状态、MinIO entry JSONL 与 `project_papers`；论文及 `user_papers` 仍保留在个人论文库。
- `session.project_id` 创建后不可修改；需要不同论文范围时新建 session，不实现会话迁移及历史引用重写。

# 模块 04：上传、解析与任务状态机

> 前置：模块 01（核心闭环）、02（Key 归属）、03（user_papers 关系、agent 工具取论文集合）。目标：上传契约、4 阶段解析的状态机、失败续跑、去重并发。

## Round 1（当前激活）

❓ **Q1 - 上传完成与校验**：上传接口何时算成功？要做哪些校验（大小上限、MIME/PDF magic、可读性、SHA-256）？上传后立即异步解析还是同步等到某阶段？

- A：流式接收，同步完成大小 / PDF magic / 可读性 / SHA-256 校验后返回 `202 + ingestion_id`；解析全程异步
- B：只存文件不校验立即返回（最快，但问题后置到解析才暴露）
- C：同步等待解析完成才返回（体验差，不可取）

➡️ 推荐答案：A。校验与解析解耦，上传即返回。

✅ 决定：**接受推荐 A。** 流式接收，同步完成大小上限 / PDF magic / 可读性 / SHA-256 校验后返回 `202 + ingestion_id`；解析全程异步，进度经接口可查。

❓ **Q2 - 状态机形态**：原型只有 `ready/failed`。排队中、运行中、已取消、部分可用、重建中如何表达？论文状态与"某次解析 run 的状态"是否要分开？

- A：分开：论文有生命周期状态；每次解析是一个 run（queued/running/succeeded/failed/cancelled），各阶段状态与 attempt 单独记录
- B：单一 `papers.status` 表达一切（最简，但阶段/尝试/取消全混在一起）
- C：不建 run 概念，仅记录"当前阶段 + 错误"

➡️ 推荐答案：A。run 模型是取消、重试、重建的基础。

✅ 决定：**接受推荐 A。** 论文生命周期状态与"单次解析 run"状态分开；run 有 queued/running/succeeded/failed/cancelled，各阶段状态与 attempt 单独记录。

❓ **Q3 - 部分可用与能力判定**：GROBID 成功但 embedding 失败时，用户能否看元数据/原文？"可搜索 / 可问答"用什么表达？

- A：阶段产物可持久化可观察；用明确 capability 字段（has_metadata / has_fulltext / has_embedding）判定能力，而非单个 status 吞掉
- B：全有或全无：任一阶段失败整篇 failed
- C：只在全文阶段做检查点，其他阶段不落盘

➡️ 推荐答案：A。能力与生命周期状态分离，用户可部分使用。

✅ 决定：**接受推荐 A。** 各阶段产物持久化且可观察；用 capability 字段（has_metadata / has_fulltext / has_embedding）判定"可搜索/可问答"，生命周期状态单独表达，失败时用户仍能用已有部分。

❓ **Q4 - 去重并发**：相同 SHA-256 同时上传时，等待并复用已有结果，还是各自启动任务？（模块 02 已定全局去重）

- A：同一 paper/版本只运行一个构建 run；其他请求关联并订阅该 run
- B：各自启动任务，最后写入覆盖
- C：后到的直接 409 拒绝

➡️ 推荐答案：A。避免重复解析，天然支持并发上传。

✅ 决定：**接受推荐 A。** 同一 paper/版本只运行一个构建 run；其他相同文件上传请求关联到该 run 并订阅其结果。

❓ **Q5 - 重试策略**：哪些错误自动重试、退避多久？哪些必须用户改配置后手动重试？

- A：网络超时 / 429 / 供应商 5xx 有界指数退避自动重试；鉴权、额度、输入非法不自动重试；每阶段幂等并记录 attempt
- B：全部手动重试
- C：全部自动重试不限次数

➡️ 推荐答案：A。自动重试只覆盖"瞬时故障"，配置类错误交给用户。

✅ 决定：**接受推荐 A。** 网络超时 / 429 / 供应商 5xx 用有界指数退避自动重试；鉴权、额度、输入非法不自动重试（等用户改配置后手动重试）；每阶段幂等并记录 attempt。

❓ **Q6 - 取消与重建**：用户能否取消进行中的解析？换 embedding 模型/分块参数后如何重建而不破坏正在使用的数据？

- A：支持协作式取消；新版本旁路构建，完成后原子切换 active version，不原地删旧 chunks
- B：不允许取消；重建 = 删除后重算
- C：首版不支持重建

➡️ 推荐答案：A。旁路构建保证切换瞬间可用。

✅ 决定：**用户自定义：不能取消，不考虑重建。**
- 不支持取消进行中的解析 run。
- 不做 embedding/分块参数的版本切换与重建；embedding 由开发者固定（模块 02 已定），用户无重建需求。
- 影响：旁路构建/active version 复杂度移除；若未来开发者更换 embedding 模型需整体迁移，但不在首版用户功能范围。

# 模块 05：内容表示、分块与向量

✅ 决定：**接受推荐 A。** chunk 记录 embedding_model + dimensions；索引参数纳入记录；首版只激活一套。

➡️ 推荐答案：A。结构化类型能提升检索质量，成本可控。

✅ 决定：**接受推荐 A。** 首版索引标题路径 + 正文 + 图表说明；表格保留结构化文本；参考文献单独标型并降低权重；公式/脚注按原始 type 处理。

# 模块 06：检索、RAG 与引用

> 前置：模块 01（问答质量承诺）、03（agent 工具取论文集合）、05（分块与向量）。目标：检索作用域、检索管线、多论文公平性、引用正确性、提示注入防护。

## Round 1（当前激活）

❓ **Q1 - 检索作用域**：语义检索针对什么范围？（模块 03 已定论文集合由 agent 工具动态获取）

- A：统一 search API 显式要求 scope（paper_id / project_id / 个人全库）；agent 工具据此检索；首版支持 paper + project
- B：只支持单篇论文检索
- C：只支持全库检索

➡️ 推荐答案：A。scope 显式化，与 agent 工具调用对应。

✅ 决定：**接受推荐 A。** 统一 search API 显式要求 scope（paper_id / project_id / 个人全库）；agent 工具据此检索；首版支持 paper + project，个人全库后续扩展。

❓ **Q2 - 检索管线**：首版用纯向量检索，还是 pgvector + PostgreSQL 全文混合？

- A：混合召回：语义 + 全文（公式/专有名词/符号互补）；reranker 作为可选阶段，不成为首版硬依赖
- B：纯向量检索
- C：向量 + reranker 必须

➡️ 推荐答案：A。混合召回在学术论文场景明显优于纯向量。

✅ 决定：**采用 PostgreSQL 关键词全文检索 + pgvector 向量相似度检索的混合召回；首版不做 rerank。**
- 关键词通道使用 PostgreSQL `tsvector` / `tsquery` + GIN 索引，补充术语和精确词项召回；不宣称使用严格 BM25。
- 首版仅针对英文论文使用 PostgreSQL `english` 全文配置；中文论文与中文关键词检索后置。
- 向量通道负责语义相似度召回；两路候选使用 RRF（Reciprocal Rank Fusion）融合并去重，再执行每篇论文限额，形成最终证据集。
- 首版不更换 PostgreSQL 16 镜像，不引入 ParadeDB、OpenSearch 或 Elasticsearch。
- rerank 后期再讨论，不属于首版验收范围。

❓ **Q3 - 多论文公平性**：一个长论文是否占满 top-k？

- A：跨范围召回后做相邻块合并、去重、按论文限额；把最终证据集与分数写入 run 记录
- B：不加限制，纯按分数取 top-k
- C：每篇论文平均分配配额

➡️ 推荐答案：A。限额 + run 记录，兼顾公平与可复现。

✅ 决定：**接受推荐 A。** 跨范围召回后做相邻块合并、去重，并按"每篇论文限额"限制进入证据集的片段数；证据集与分数写入 run 记录。

❓ **Q4 - 证据不足行为**：相似度多低算证据不足？证据不足时 agent 怎么表现？（呼应模块 01 Q3 质量承诺）

- A：定义证据集数量/分数下限；不足时 agent 明说"论文中没有相关内容"，不硬答
- B：只要有任一 chunk 就作答
- C：阈值默认很宽松，基本不触发

➡️ 推荐答案：A。把"无证据"做成显式状态，而不是硬凑答案。

✅ 决定：**接受推荐 A。** 定义证据集数量/分数下限；不足时 agent 明说"论文中没有相关内容"，不硬答、不用通用知识填充。

❓ **Q5 - 引用正确性**：LLM 生成的引用是自由文本，还是只能引用证据集内的 citation ID？服务端校验吗？

- A：模型只能选择证据集中已有 citation ID；服务端校验 ID 与作用域；展示格式与模型输出解耦
- B：引用是自由文本，随模型发挥
- C：模型随意引用，不做校验

➡️ 推荐答案：A。引用必须是证据子集，服务端兜底。

✅ 决定：**接受推荐 A。** 模型只能从证据集中选择已有 citation ID；服务端校验 ID 存在且属于作用域；展示格式（页码/链接）与模型输出解耦。

❓ **Q6 - 提示注入防护**：论文文本中夹带的指令如何避免改变 agent 行为？

- A：检索内容始终标记为不可信引用材料；工具权限由服务端控制；不允许文档内容直接拼成高优先级提示词
- B：不处理，论文原文直接进 prompt
- C：解析时清洗文档内容中的指令

➡️ 推荐答案：A。边界在"材料可信级别"而非内容清洗。

✅ 决定：**用户选择 B：不处理提示注入。** 论文原文直接进 prompt，不做不可信材料标记或服务端工具权限控制。
- 说明：存在文档内容夹带指令改变行为的风险；简历项目可接受，不适用于生产部署。

# 模块 07：Agent 与对话行为

> 前置：模块 01（核心闭环）、06（检索管线、引用校验、无证据状态）。目标：默认 agent 行为、message/run 模型、上下文策略、并发与取消。

## Round 1（当前激活）

❓ **Q1 - 默认 agent 行为**：首版默认 agent 是什么形态？（模块 03/06 已定：论文集合与检索都通过工具）

- A：受限 RAG agent：可多步调用检索/取原文工具，但工具集固定、回合数有上限、证据范围受限
- B：单轮 RAG 链：每次提问固定"检索 → 拼 prompt → 生成"，不循环
- C：完全自主 agent：可自由调用任意工具、任意多步

➡️ 推荐答案：A。展示 agent 能力同时可控、可解释。

✅ 决定：**接受推荐 A。** 受限 RAG agent：可多步调用检索/取原文工具，工具集固定、回合数有上限、证据范围受限。

❓ **Q2 - message / run 模型**：用户消息与助手回答是 message；"每次生成尝试"与 message 如何区分？

- A：message 存内容（不可变）；run 记录单次生成尝试（模型、配置、检索证据、工具调用、状态、usage）；重试/再生成 = 新 run
- B：message 即全部，不建 run
- C：message 与 run 混为一谈

➡️ 推荐答案：A。run 是取消、重试、审计、复现的单位。

✅ 决定：**采用 pi agent 风格的统一 Entry 日志，不建立 Agent run 或独立 message 持久化模型。** 消息、工具调用与结果、上下文压缩、模型切换、usage、引用证据等都表示为带类型和序号的 entry；会话 JSONL 保存完整追加式 entry 日志。AgentScope 只作为执行引擎，其事件由适配层转换为 Paper Agent entry/API 事件；框架内部 `reply_id` 不提升为产品领域概念。

❓ **Q3 - 上下文策略**：长会话超出模型窗口时怎么处理？丢旧消息、摘要，还是检索历史？

- A：保留不可变消息历史；每个 run 构造有预算的上下文，先裁剪工具噪声，必要时用版本化摘要压缩旧对话；记录实际输入范围
- B：简单截断最旧消息
- C：不处理，超出窗口直接报错

➡️ 推荐答案：A。摘要压缩比粗暴截断保真。

✅ 决定：**上下文从 JSONL entry 列表动态重建。** 上下文压缩由 AgentScope 的压缩能力执行，但压缩行为与结果也写成 entry；模型切换等影响上下文解释的行为同样进入日志。会话不能只保存最终消息快照。

❓ **Q4 - 并发与取消**：同一会话能否同时启动多个 run？用户中断时是否保留部分回答？

- A：首版每会话最多一个 active run；允许中断并保留标记为 incomplete 的部分输出，不当成正常 assistant message
- B：允许同一会话并发多个 run
- C：不允许中断，必须等生成完成

➡️ 推荐答案：A。单 active run 语义简单，incomplete 保留诚实。

✅ 决定：**同一 session 只运行一个 Agent loop，但允许 pending 消息，并参考 pi agent 区分两种投递方式。**
- `steering`：当前 Agent loop 尚未结束时，在框架允许的下一个安全边界注入，影响当前执行方向。
- `follow_up`：等待当前回答完成后，再作为下一轮用户输入继续处理。
- 正常交互不支持多个并行 Agent 请求；pending 仅表示同一用户在当前 Agent 工作期间主动追加的 steering/follow-up。
- 短时间重复发送相同 prompt 不进入 pending 队列：网络重试由 `Idempotency-Key` 去重，异常高频提交由用户/session 级速率控制拒绝。
- Web 后端不照搬 pi 的纯内存 pending：Redis 分别维护 `pending:steering` 与 `pending:followup` 两个 FIFO 队列，并由 AOF 保护；默认均采用 `one-at-a-time`。
- 每个 session 通过带租约的 executor lock 保证只有一个 Agent loop。steering 在当前 assistant turn 及工具批次结束后的安全边界取出；follow-up 仅在 Agent 原本准备停止时取出。
- pending 消息排队时不是 session entry；实际投递给 Agent 时才原子地从 pending 队列转成正式 user entry。当前 executor 崩溃时，本次生成标记 `aborted`，pending 仍保留；客户端用已保存的模型选择与 Key 触发恢复。
- 用户主动停止或执行中断时，保留已经生成的 assistant message，写入 `stopReason: "aborted"`；上下文重建时仍包含该 entry，沿用 pi agent 语义。

❓ **Q5 - 工具可见性**：前端/客户端需要看到工具调用的参数、进度和结果到什么程度？

- A：流中暴露安全的阶段/工具摘要与 citation；不回显密钥、完整 prompt、可能很大的原始工具结果
- B：工具调用对前端完全不可见
- C：完整暴露工具参数与原始结果

➡️ 推荐答案：A。可见但脱敏。

✅ 决定：**接受推荐 A。** 流式响应中暴露安全的阶段/工具摘要与引用；不回显密钥、完整 prompt、很大的原始工具结果。

❓ **Q6 - 模型失败与降级**：模型超时、上下文超长、内容策略拒绝时，是否自动切换别的模型？

- A：只对可重试的传输错误自动重试同配置；不静默换模型；降级必须由配置声明并在 run 中记录
- B：失败即自动换备用模型
- C：失败直接报错，不做任何降级

➡️ 推荐答案：A。换模型改变行为，必须显式而非静默。

✅ 决定：**接受推荐 A。** 只对可重试的传输错误自动重试同配置；不静默换模型；降级必须显式配置并在执行记录中标注。

# 模块 08：会话持久化与一致性

> 前置：模块 03（论文集合由 agent 工具取）、07（会话 JSONL 存 entry 列表、AgentScope 处理上下文重建）。目标：消息权威源、写入确认时点、崩溃恢复、历史操作。

## Round 1（当前激活）

❓ **Q1 - 消息权威源**：会话内容（用户消息、agent 回复、工具调用记录）最终以谁为准？原型是 Redis 热 + MinIO 冷 + 定时刷回，但崩溃时两边都可能含最新数据。

- A：PostgreSQL 作为消息权威源（查询/审计/恢复最省心）；MinIO JSONL 仅作导出归档；Redis 只做流与热缓存
- B：JSONL 为准（存 MinIO/Redis），数据库只存会话元信息（贴合原型，但恢复逻辑自己写）
- C：Redis 为准 + 定期落 JSONL（丢最近几分钟可接受）

➡️ 推荐答案：A。数据库当权威源最省心，Redis/MinIO 退化为缓存与归档。

✅ 决定：**用户选择 B：JSONL 为准（存 MinIO/Redis），PostgreSQL 只存会话元信息（id/title/context 等）。** 维持原型模型。

❓ **Q2 - 写入确认时点**：用户发消息后，什么时候算"已保存"？（模块 01 质量承诺：不丢已确认的用户消息）

- A：用户消息先持久化成功，才启动 agent 回答；回答增量可边流边存，完成/中断时落最终状态
- B：用户消息只进 Redis/内存，直接开始回答
- C：整轮对话完成后再一次性保存

➡️ 推荐答案：A。先持久化用户输入，再开始消耗成本执行。

✅ 决定：**用户消息先写入 Redis List，随后立即开始回答；Redis 开启 AOF，采用 `appendfsync everysec`。** “已确认”定义为成功追加到 Redis；普通进程/服务重启可从 AOF 恢复，接受极端主机故障时约 1 秒的尾部数据风险。MinIO JSONL 仍在会话空闲时刷回并作为冷持久历史。

❓ **Q3 - 存储粒度与追加**：消息/事件怎么追加到会话？（整对象重写 vs 独立小对象）

- A：每条消息/事件一个独立小对象（按 seq 命名）或用支持追加的存储，避免整文件重写
- B：整条会话一个 JSONL 对象，追加时整对象重写（长会话代价高、并发易覆盖）
- C：Redis list 追加，定期整体刷成 JSONL 对象

➡️ 推荐答案：A。追加友好，避免重写与覆盖竞争。

✅ 决定：**用户选择 C：Redis list 追加，定期整体刷成 JSONL 对象。**
- 影响：单会话 JSONL 整对象重写的成本与并发覆盖风险仍在，靠"每会话单写者/串行刷回"约束（模块 09 幂等与并发里处理）。

❓ **Q4 - 崩溃恢复语义**：进程 / Redis / MinIO 中途故障后，用户看到什么？

- A：已确认的用户消息不丢；未完成的回答标记为 interrupted/failed，用户可重试
- B：回滚到上次刷回点（丢最近几分钟）
- C：不处理，能恢复多少算多少

➡️ 推荐答案：A。确认过的输入不丢，未完成的诚实标记。

✅ 决定：**接受推荐 A。** 已确认的用户消息不丢；未完成的回答标记为 interrupted/failed，用户可重试。（"已确认"定义见 Q2：已写入 Redis list。）

❓ **Q5 - 历史操作**：会话是否支持改名、删除、编辑消息、从旧消息分支、导出？

- A：首版支持改名、删除、导出；不做原地编辑，重试/改问生成新分支，保留审计
- B：只支持删除和改名
- C：只读，不支持任何修改

➡️ 推荐答案：A。编辑消息会破坏历史一致性，留到未来。

✅ 决定：**接受推荐 A。** 首版支持会话改名、删除、导出；不做原地编辑消息，重试/改问生成新分支，保留审计。

- 删除活动会话时，由后端先终止当前 Agent 生成，将已生成的部分 assistant entry 标记为 `aborted`，清空 steering/follow-up pending 队列，再删除 PostgreSQL 会话元数据、Redis 状态与 MinIO JSONL；不要求用户预先单独停止。

❓ **Q6 - 刷回触发**：原型把"切换页面 / 关闭会话"当刷回触发，但这是前端行为、不可靠。首版如何兜底？

- A：以"写入即持久化"为准（见 Q1–Q3），定时刷回只是兜底/归档；不依赖前端事件
- B：保留原型：定时扫描活跃会话 + 前端触发刷回
- C：不做定时，完全靠写入路径

➡️ 推荐答案：A。持久化责任放回写入路径，前端事件只是体验优化。

✅ 决定：**用户自定义：空闲计时刷回。** 每次有新消息 append 都重置计时；计时停止（空闲）时把 Redis list 刷到 MinIO JSONL；切换页面/退出不做特殊处理，后台继续生成。
- 影响：无前端事件依赖；持久化节奏 = 空闲触发，简单且贴合原型 JSONL 为准。

# 模块 09：API、流式与后台任务

> 前置：模块 04（解析 run）、07（agent 执行、工具可见性、AgentScope）、08（Redis list + JSONL 刷回）。目标：API 组织与版本、问答流形态、事件 schema、错误契约、Celery 边界。

## Round 1（当前激活）

❓ **Q1 - API 组织与版本**：API 顶层资源怎么组织、要不要版本前缀？（考虑 Yaak 联调与简历展示）

- A：统一 `/v1` 前缀；论文/项目/会话/问答按资源组织，顶层 ID 稳定，创建可嵌套
- B：不搞版本前缀，直接 `/papers`、`/projects` 等
- C：按领域深层嵌套 URL（如 `/users/{id}/projects/{id}/sessions`）

➡️ 推荐答案：A。版本前缀 + 顶层资源，简单清晰。

✅ 决定：**接受推荐 A，并按 Entry 模型修正。** API 统一使用 `/v1` 前缀；论文、项目、会话等采用 `/papers`、`/projects`、`/sessions` 等稳定资源路径，创建关系时可适度嵌套。Agent 对话不提供长期 `/runs` 资源。

❓ **Q2 - 问答流形态与恢复边界**：用户提问后，回答怎么给到前端？本地 AgentScope 2.0.6 已有“创建执行 + SSE 订阅 + Redis 短期事件 replay”的 App 层实现，但 run 结束后会清理事件，且没有独立的持久化 RunRecord。

- A：沿用 AgentScope 两步式：POST 创建执行 → 返回执行 ID → SSE 订阅；执行任务和 LLM Key 只驻留进程内存，Redis 仅保存短期事件用于客户端断线重连；后端进程重启时 active run 失败，不承诺跨进程恢复
- B：直接 POST 返回流式响应；Key 仅活在请求期间，实现最简单，但客户端断线即失去本次流
- C：自建持久化 run/event 和临时 secret 托管，使 active run 可跨进程恢复（明显扩大首版安全与持久化范围）

➡️ 推荐答案：A。它复用框架已有能力，支持客户端短暂断线续流，同时诚实限定为单机进程级恢复；不为简历项目引入可恢复 secret 托管。

✅ 决定：**按 Session + Entry 模型采用进程内临时生成。** 用户向 session 追加消息后启动 Agent；SSE 按 session 订阅增量事件，Redis 仅保存短期事件供客户端断线重连。Agent 生成状态不形成长期 run。后端进程重启时本次生成中断，由用户重试，不承诺跨进程恢复。

❓ **Q3 - 事件 schema**：解析进度、agent 回答、工具调用这些事件，要不要统一信封？AgentScope 已有细粒度 `AgentEvent` 联合类型，但它是框架内部事件，不等于 Paper Agent 的稳定公共 API。

- A：统一 Paper Agent 事件信封（event_id / type / resource_id / sequence / timestamp / data / schema_version）；agent 事件在适配层从 AgentScope `AgentEvent` 映射，解析任务使用自己的领域事件类型
- B：各接口自定义响应格式，不统一
- C：公共 API 直接暴露 AgentScope 原始事件；解析进度另用一套格式

➡️ 推荐答案：A。统一信封让前端只要写一套解析。

✅ 决定：**接受推荐 A。** 公共 API 统一使用 Paper Agent 事件信封，包含 `event_id`、`type`、`resource_id`、`sequence`、`timestamp`、`data`、`schema_version`；AgentScope `AgentEvent` 由适配层映射，解析任务使用同一信封下的领域事件类型。

❓ **Q4 - 错误契约**：客户端靠什么稳定处理错误？

- A：统一错误格式（稳定 `code` + message + request_id + 可选 field/details），供应商原始错误只进日志
- B：每个接口自己定错误格式
- C：只有 HTTP 状态码，无结构化错误体

➡️ 推荐答案：A。稳定 code 是前端分支判断的基础。

✅ 决定：**接受简化方案。** 所有 API 使用统一最小错误体：字符串 `code`（`snake_case`）、人类可读 `message`、用于日志关联的 `request_id`；HTTP 状态码负责错误大类。`details` 不作为通用必填字段，仅参数校验等确有需要的场景按需返回。供应商原始错误只进入脱敏日志。

❓ **Q5 - Celery 边界**：什么必须进队列，什么留在请求进程？（原型 Celery + Redis）

- A：上传确认后的解析/embedding/清理进 Celery；鉴权、资源变更、轻量检索留请求路径；agent 执行是否进队列由 Q2 流形态决定
- B：所有耗时操作都进队列
- C：不用 Celery，全部在请求内完成

➡️ 推荐答案：A。异步边界按"是否可后台化"切分。

✅ 决定：**接受推荐 A。** 上传确认后的解析/embedding/清理进 Celery；鉴权、资源变更、轻量检索留请求路径。Agent 生成留在 FastAPI 进程内，不再套 Celery。

❓ **Q6 - 幂等与并发**：上传、创建执行、重试、删除哪些需要幂等键或版本检查？

- A：成本高的 POST（上传、创建执行）支持 Idempotency-Key；更新用版本/ETag 防丢失更新；后台任务本身幂等
- B：不做幂等，靠唯一约束兜底
- C：只有上传做幂等

➡️ 推荐答案：A。Idempotency-Key + 版本检查成本低收益高。

✅ 决定：**接受推荐 A。** 成本高的 POST（上传、创建执行）支持 Idempotency-Key；更新用版本/ETag 防丢失更新；后台任务本身幂等。

# 模块 10：安全、运维与可恢复性

> 前置：模块 02（多账号、Key 归属）、04（解析 run）、08（Redis/JSONL 权威）、09（API/错误/幂等）。目标：威胁模型、解析隔离、数据保护、可观测性、备份恢复、部署拓扑。

## Round 1（当前激活）

❓ **Q1 - 威胁模型**：首版主要防谁——误操作、恶意 PDF、局域网其他用户，还是公网攻击者？

- A：覆盖"不可信 PDF + 越权访问（多账号）+ 供应商故障"；若公网部署按反向代理安全基线，不承诺完整企业安全
- B：只防误操作，信任局域网
- C：按公网多租户全量加固（超出简历项目范围）

➡️ 推荐答案：A。防护力度与部署形态匹配。

✅ 决定：**接受推荐 A。** 覆盖"不可信 PDF + 多账号越权访问 + 供应商故障"；公网部署按反向代理安全基线，不承诺完整企业安全。

❓ **Q2 - 解析隔离**：PDF 是不可信输入，解析器输出也不可信。需要哪些限制？

- A：上传大小/页数/超时/内存/并发上限；文件名与 MIME 不作信任依据；解析器输出路径按不可信处理
- B：不设限制
- C：沙箱/容器级强隔离（重，超出首版）

➡️ 推荐答案：A。资源上限 + 不信任外部声明的路径。

✅ 决定：**接受推荐 A。** 上传大小/页数/超时/内存/并发上限；文件名与 MIME 不作信任依据；解析器输出路径按不可信处理。

❓ **Q3 - 密钥与数据保护**：需要哪些数据保护措施？

- A：全链路 TLS；数据库/对象存储不公开；密码哈希（如 argon2/bcrypt）；JWT 密钥环境变量；LLM Key 后端仅转用不持久化
- B：只保证登录可用
- C：应用层密钥加密 + KMS 等全套（超出范围）

➡️ 推荐答案：A。务实覆盖，不引入企业级基础设施。

✅ 决定：**接受推荐 A。** 全链路 TLS；数据库/对象存储不公开；密码哈希；JWT 与 LLM 密钥由部署环境提供，不持久化到业务数据。

❓ **Q4 - 可观测性**：首版需要哪些日志/指标才能定位用户问题？

- A：request_id / run_id / paper_id 串联日志；记录解析阶段时延、成功率、供应商错误码、token 用量；绝不记录论文全文、prompt、密钥
- B：只有标准 FastAPI 访问日志
- C：完整指标面板与告警（超范围）

➡️ 推荐答案：A。串联日志 + 结构化字段，够排查问题。
